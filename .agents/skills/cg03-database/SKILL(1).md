# CG03 Database

## Required context

Before changing the database:

1. Read `database.md`.
2. Inspect `PortfolioDbContext`.
3. Inspect relevant EF Core entity configurations.
4. Inspect existing migrations.
5. Inspect repositories using the affected tables.
6. Inspect application rules that depend on the data.

Do not infer schema from memory when `database.md` or migrations provide the
answer.

## Persistence stack

Use:
- PostgreSQL
- Entity Framework Core 10
- Npgsql

Use EF Core migrations for application-managed schema changes.

## Repository boundary

Database queries belong in feature-specific repository implementations.

Example:

IProjectRepository
→ ProjectRepository
→ PortfolioDbContext

Do not place EF Core queries in Controllers.

Do not use generic repositories unless there is a demonstrated requirement.

## Unit of Work

Use `PortfolioDbContext` as the EF Core unit of work.

Do not introduce an `IUnitOfWork` / `UnitOfWork` wrapper solely to proxy
`SaveChangesAsync()`.

Use one scoped DbContext for changes that belong to one application operation.

Use explicit EF Core transactions where atomic multi-step behavior requires it.

## Schema review checklist

For every schema change consider:
- primary key;
- foreign key;
- nullability;
- unique constraint;
- check constraint;
- default value;
- cascade/restrict behavior;
- timestamps;
- indexes;
- migration compatibility;
- existing production data.

Do not add columns simply because they may be useful later.

## Indexes

Add an index only when supported by an actual access pattern or constraint.

Consider:
- WHERE predicates;
- JOIN keys;
- ORDER BY;
- uniqueness;
- partial indexes;
- composite column order.

Avoid redundant indexes.

For performance work, use query plans when practical.

## Query rules

For read-only queries:
- prefer projection;
- use `AsNoTracking()` when tracking is unnecessary;
- avoid N+1 queries;
- avoid unnecessary `Include`;
- select only data needed by the response.

For complex queries, inspect generated SQL when useful.

## Migrations

Do not edit previously applied migrations.

Create a new migration.

Before generating a migration:

1. verify entity changes;
2. verify configuration changes;
3. inspect the expected SQL impact.

Typical command:

```bash
dotnet ef migrations add <MigrationName> \
  --project src/Portfolio.Infrastructure \
  --startup-project src/Portfolio.Api
```

Inspect the generated migration before applying it.

Never run destructive production migrations casually.

## Transactions

Use transactions when multiple changes form one business operation.

Examples:
- Resume version allocation;
- changing active Resume;
- reorder;
- replacing related records;
- coordinated metadata updates.

Keep the transaction as short as practical.

Do not perform slow network calls inside a database transaction unless the
workflow specifically requires it and the failure semantics are understood.

## Resume versioning

Follow the versioning rules defined in `database.md`.

Important invariants:
- version is generated by the backend;
- EN and VI counters are independent;
- sequence is not reused after deletion;
- changing metadata does not generate a version;
- replacing a file creates a new version;
- only one Resume may be active per language.

Version allocation and metadata persistence must be concurrency-safe.

## Multilingual data

The system uses English (`en`) and Vietnamese (`vi`) translation tables.

Preserve `(entity_id, locale_code)` relationships.

Do not duplicate translated values into base entities without an explicit
schema change.

## Verification

For database changes:
- build the solution;
- run relevant tests;
- inspect the generated migration;
- verify constraints/indexes;
- test important repository behavior against PostgreSQL where practical.
